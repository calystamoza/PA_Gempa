## Post-Evaluation Review — Analisis SQL Parameter (2026-07-08)

> Setelah evaluasi live selesai, dilakukan inspeksi mendalam terhadap SQL yang dihasilkan
> vs. SQL yang seharusnya dihasilkan berdasarkan makna semantik pertanyaan.
> Ditemukan **3 bug SQL semantik** yang tidak terdeteksi oleh evaluator otomatis
> karena sistem tetap mengembalikan data yang valid (hanya kurang tepat secara semantik).

### Bug yang Ditemukan & Diperbaiki

| No | Pertanyaan | Bug SQL | Perbaikan |
|----|-----------|---------|-----------|
| **#13** | *"Gempa terbesar dalam **data terbaru** kita?"* | Tidak ada filter `year` → mengembalikan M9.0 Aceh 2004 (sepanjang waktu), bukan data terbaru | Post-processing di `process_query()`: frasa "data terbaru" → inject `year = DATA_TAHUN_TERBARU` otomatis |
| **#24** | *"Tampilkan 10 gempa **terbaru**"* | `ORDER BY magnitude DESC` (terbesar) bukan `ORDER BY year DESC` (terbaru) | `build_sql()` untuk `list` intent sekarang menggunakan `order_by` dari LLM intent, bukan hardcode `magnitude` |
| **#25** | *"5 gempa paling **dangkal** di Kalimantan"* | `ORDER BY magnitude ASC` (terkecil) bukan `ORDER BY depth ASC` (terdangkal) | Sama dengan #24 — `list` SQL builder kini respek terhadap `order_by: "depth"` yang dihasilkan LLM |

### Perubahan pada `rag_engine.py`

1. **`SAFE_COLUMNS`** — ditambah `"date"` sebagai kolom ORDER BY yang aman
2. **`build_sql()` — `list` intent** — `ORDER BY` sekarang dinamis dari `intent.order_by` (bukan hardcode `magnitude`)
3. **`INTENT_SYSTEM` prompt** — panduan ORDER BY untuk `list` diperjelas per kriteria (terbesar/terdalam/terdangkal/terbaru/terlama)
4. **`process_query()` — post-processing** — deteksi frasa "data terbaru / data paling baru" → otomatis inject `year = DATA_TAHUN_TERBARU` jika tidak ada filter temporal
5. **`DATA_TAHUN_TERBARU`** — diubah dari konstanta hardcode menjadi nilai **dinamis dari database** (`SELECT MAX(year) FROM earthquakes`) sehingga tidak perlu update manual jika ada data 2026 atau seterusnya

### Catatan Akurasi

> Ketiga bug ini **tidak mempengaruhi akurasi evaluasi live (100%)** karena:
> - Evaluator mengecek apakah SQL sesuai *pola intent* (bukan kebenaran semantik)
> - Jawaban yang dihasilkan tetap valid dan relevan dari sisi seismologi
>
> Namun secara **semantik**, kasus #13 mengembalikan jawaban yang berbeda dari maksud user,
> dan kasus #24-#25 mengembalikan urutan yang tidak sesuai ekspektasi.
> Perbaikan ini meningkatkan kualitas nyata sistem tanpa mengubah skor evaluasi resmi.
